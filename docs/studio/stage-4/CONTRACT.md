# Stage 4 agreed implementation contract

Status: implementation authorized after all ten role briefs and three proposals. Stage 3 acceptance remains tied to a288074 and CI 39864420684; the open performance and physical/native validation limits carry forward.

## Decisions and resolved disagreements

- Story identity uses `/[locale]/p/project-{Project.slug}` and `/[locale]/p/unit-{Property.slug}`. The same fresh authorized resolver supplies HTML, metadata, JSON and canonical paths. Missing and denied subjects are indistinguishable. No raw reference record reaches the browser.
- Portfolios accept only a public real-reference project interest or an authorized fictional unit. A demo-project grouping requires explicit unit selection. Existing unit-only foreign keys and legacy routes remain intact; separate reference relations are additive.
- API names follow BACKEND-PROPOSAL: `/stories/[slug]`, `/portfolios` and child `/items` and `/dossier`, `/office/comparison`, `/office/advisor`, `/office/threads/[id]/messages`, `/office/private-collection`, `/project-enquiries`, and the compatible `/viewings` adapter. Office route presentation may use section links rather than duplicating each screen.
- Sources, native amounts, price basis, dates and unknowns remain attached to the subject. Numeric derivations require compatible operands. A reference project never inherits a fictional unit's area, yield, schedule, availability or permit.
- The privacy seam requires durable minimal flags/version, including restrictions from an unsaved or cancelled conversation. New persisted portfolio/workflow/message writes respect no-save; communications respect no-share; schedules respect no-book. Explicit versioned settings can relax flags; stale snapshots cannot reinstate cleared flags or silently clear new ones. Reading, deletion and cancellation remain possible. **Owner-only dossier generation/download is read-only and allowed under no-save/no-share**: it persists no new client content and sends nothing to another person. This narrows the backend proposal's blanket dossier restriction.
- Export reauthorizes the board before rendering and again before release. A changed or inaccessible saved entry gives a neutral review-required response without hidden identity/count. An explicit visible-set export may follow review; never silently produce a partial dossier. Downloaded documents cannot be recalled.
- Share scope is an explicit copy of an access-controlled canonical URL with an explanation that the recipient needs their own access. Label it accurately; no token, grant, email or external message is created. This resolves the Story proposal's preference for a new revocable share artifact without adding unrequested entitlement delegation.
- Named advisors are persisted fictional demo profiles with explicitly authored availability and timestamps, not simulated online presence. Threads authorize the client and current assigned advisor; attachments resolve within client visibility. No automatic Brief/history copying, generated human reply or fake read receipt.
- Lenis is required by the brief on editorial pages. Implement it only on Story, with reduced-motion opt-out, native touch/nested controls, cleanup and verified keyboard/anchor behavior. Native scroll remains the fallback; a demonstrated failure requires a documented alternative, not silent omission. This resolves the motion proposal's native-first preference.
- Viewing calendar represents requests, never invented available slots. Unit booking and real-project enquiry are distinct; local times resolve server-side with explicit DST ambiguity/nonexistence rejection and a three-city confirmation.

### Implemented backend handoff and upgrade boundary

The Story resolver returns the native amount plus the other five supported display conversions. Unknown real-reference metrics and incomplete schedules remain explicitly unavailable. Published developer facts reuse the grounded developer projection; neither raw reference JSON nor synthetic real-project residences are returned.

`getDossierData(id, viewer, preferences, { reviewVisible?: boolean })` rejects an inaccessible saved entry with neutral `portfolio_changed`; an explicit visible-set review may export only the authorized entries. Owner-only read-only generation/download remains permitted under both no-save and no-share. The export adapter must compare a fresh projection before releasing bytes.

`GET/PATCH /api/v1/office/privacy` reads/updates the durable policy with an expected `version`. Explicit Office settings are the only relaxation path. A Concierge `privacy.replace` patch that tries to relax an active durable flag returns `privacy_settings_required`; the client should link to Office privacy settings. New restrictive text is persisted before lease acquisition or provider selection, including a cancelled or unsaved request. Older client/history flags cannot silently reapply an explicitly cleared policy. Legacy Consultant external processing, history writes, and direct shortlist/viewing/handoff tools consume the same policy.

`PATCH /api/v1/office/advisor/availability` accepts only `{ availability }` for the currently authenticated advisor's own persisted Demo profile; its timestamp is server-authored. There is no live-presence simulation. Assignment and exact reviewed attachment references govern secure-thread access; assignment never widens a client's inventory visibility.

Concurrent matching request IDs create at most one effect/receipt. A racing request may receive `409 conflict`; retrying the same ID and unchanged input returns the existing effect. A reused ID with changed input returns `idempotency_conflict`. Portfolio edits additionally require the current board version. Deletion and cancellation remain available under restrictive policy.

The applied initial Office migration is immutable. The additive `20261023020100_office_privacy_backfill_guard` closes malformed non-boolean legacy flag values conservatively by setting all three durable restrictions, without changing conversation text. Missing/null flags cause the earlier migration's NOT NULL constraint to stop deployment before the follow-up; this is a documented closed failure requiring explicit review, not a successful automatic migration. Fresh installs, valid legacy upgrades, malformed-string repair, and these stopped upgrades are separately tested in `docs/reviews/stage-4/validation/migration-stage4.json`.
