# Stage 4 · Private Office proposal

Status: discovery only; no approved shared contract or feature implementation. Source baseline: a288074, Stage 3 accepted and its hosted CI green. This proposal implements the [Private Office brief](../MASTER-BRIEF-V2.md) within the selected Noir Atlas system. No browser, database or visual acceptance run was performed for this discovery.

## Product decision

`/[locale]/office` is the client's considered collection and next-step workspace. A named portfolio is the central object. Conversation finds candidates; the Office lets the client review, compare, export and request a next step without losing source qualifications. Keep the workspace quiet: a portfolio board is the primary view, with an advisor rail and an upcoming-request summary. Avoid dashboard statistics with no client decision attached.

At 1440px, use an editorial title and modest action row, a two-column board region and a narrow advisor/upcoming rail. At 1024px, move the rail beneath the board. At 375/390px, use a single reading column, explicit section links and a compact comparison tray that reserves its own space. The Office scrolls normally; it does not inherit the map's fixed-height sheet. One expanded board shows ordered cards with a source/availability line before actions. Renaming is an inline task, not a permanently visible form on every board.

Reuse existing typography, spacing, surfaces, focus treatment and light/dark tokens from `src/styles/tokens.css` and the design-system primitives. Use the supplied display/UI/Arabic/Amiri fonts. Existing `/art/property-0.svg` through `property-5.svg` are architectural illustrations for fictional units, not photographs of reference projects. Reference boards may use a map/place composition or neutral editorial cover with an explicit illustration label. No generated real-project render, fabricated advisor portrait or unlicensed image is needed.

## Main journeys

**Portfolio.** Explicit Add to Portfolio opens a small chooser with existing boards and one name field for a new board. The action states what will be saved; the successful response returns the durable board ID. A REAL_REFERENCE project card says “Project reference · residences on request”; a fictional unit says “Demo unit.” A fictional project alone cannot be saved: select an authorized unit from it first. Duplicate saves are idempotent. Rename preserves selection; remove offers an accessible undo only if the server supports a real inverse. Delete a whole board requires one concrete confirmation. A no-save conversation preference cannot be silently bypassed by an AI proposal; a later direct client save must explicitly resolve that restriction rather than imply consent.

**Compare.** Select two to four typed entries. The tray names each selected entry, allows removal and explains the four-item limit. Compare original currencies first, then optional indicative display conversions with static FX/date/basis. Reference starting prices and exact demo-unit prices are not equivalent; label their basis in each column. Unknown area/yield/schedule stays unknown. Mobile offers a labeled, keyboard-focusable horizontal table with sticky row labels and a visible scroll cue, plus an accessible stacked reading view if needed. The selected set remains the same across languages and display preferences.

**Dossier.** One click exports the current authorized board in both languages, with the viewer's preferred script first. It does not email or create a public link. Include cover, purpose/optional explicitly shared Brief excerpt, named entries, native values, any derived conversion formula/date, source links with precision-aware dates, availability/evidence limits and generation timestamp. Separate reference projects from fictional units. No portfolio total implying comparable prices when bases differ. Reauthorize the complete export before generating; if a saved entry is no longer accessible, stop with a neutral review-needed message and let the user export the visible set explicitly. Do not silently issue an incomplete dossier. A previously downloaded PDF cannot be remotely revoked; avoid any such promise.

**Viewings.** A simple week/month calendar plus agenda shows _requests_, not invented free slots. The client selects one preferred time and up to two alternatives, in-person/video mode and Dubai/Cairo/London time zone. Before submission, show the chosen local time, date, zone and corresponding times in the other two cities. Submit means “Request sent”; only a staff-confirmed slot can be “Confirmed.” A reference project leads to “Enquire about residences / request an introduction” in the assigned advisor thread, optionally including preferred call times as message context. It never promises a particular residence or creates a demo-unit viewing behind the scenes.

**My Advisor.** Show the actual assigned staff identity, supported languages and explicit availability state with its basis/update time. In the demo, use a persisted, clearly fictional advisor name and genuinely authored availability/timestamp, identify the advisor as Demo, and show unknown if that declaration is absent. No green online dot, fabricated last-seen time or simulated typing. If no assignment exists, show “An advisor has not yet been assigned” and an explicit assignment request. A persisted thread identifies its participants, message timestamp and sent/failed state. Only confirmed server persistence earns “Sent”; no read receipt without an actual receipt. A request to send is distinct from saving a draft; no auto-sharing of the Concierge Brief.

**Private Collection.** Guest: explain access without previewing private titles, counts, coordinates or thumbnails. Unverified client: show the generic verification route. Verified-only access requires the current verified role and verification state; private invitations require an explicit current per-client grant. Developer partners do not inherit either entitlement. Authorized collection cards use the same qualified evidence treatment. Revocation removes details from board, compare, API, AI, thread attachments and PDF at the next authorized read; stale grants never survive through cached DTOs.

## Proposed route and DTO contract (for joint agreement)

These are proposed names, not claims that routes exist. Keep legacy endpoints working through adapters to shared services; avoid separate business rules.

| Surface / action     | Proposed route                                               | Essential contract                                                                                                              |
| -------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| Office overview      | `GET /[locale]/office`                                       | Authenticated OfficeDTO with authorized board summaries, viewer preferences, own upcoming requests and assignment.              |
| Board detail         | `GET /[locale]/office/portfolios/[id]`                       | Owner-scoped PortfolioDTO; ordered entries and revision.                                                                        |
| Board operations     | `/api/v1/office/portfolios` and `/[id]/entries`              | Create/rename/add/remove/delete, strict validation, revision/idempotency semantics, server-derived owner.                       |
| Compare              | `GET /[locale]/office/compare` / API equivalent              | Two–four deduplicated EntityRefs, all reauthorized, shared source-aware comparison rows.                                        |
| Export               | `GET /api/v1/office/portfolios/[id]/dossier`                 | Read-only authorized binary download; locale/digits/display parameters validated; private/no-store.                             |
| Viewings / enquiries | `/[locale]/office/viewings`, `/api/v1/office/viewings`       | Authorized unit request only; UTC instants + original zone/mode/status. Reference enquiries use the assigned thread.            |
| Advisor thread       | `/[locale]/office/advisor`, `/api/v1/office/thread/messages` | Current assignment/participant authorization, bounded cursor pagination, idempotent send, typed optional authorized references. |
| Private inventory    | `/[locale]/office/private`                                   | Fresh capability gate and item-by-item authorization; opaque not-found behavior.                                                |

- **EntityRef:** discriminated REAL_REFERENCE project interest versus authorized fictional unit, with canonical ID; fictional-project IDs require unit selection; never infer type from display name or substitute a unit for a project.
- **OfficeDTO:** minimal client display identity, current capabilities, preferences, authorized PortfolioSummary list, RequestSummary list, AdvisorAssignment or null. No email/private IDs in public bootstrap.
- **PortfolioDTO / EntryDTO:** board ID/name/revision/updatedAt, ordered entry IDs, freshly resolved title/slug/evidence/image/availability capabilities. Persist refs and user-authored notes only under explicit scope; do not trust stored factual snapshots on replay.
- **EvidenceValue:** raw native amount/currency or null; optional conversion with rate/as-of/method; source IDs/URLs/basis/date precision; explicit unknown. Reuse Concierge grounding/source types where possible.
- **ViewingDTO:** authorized unit target, preferred UTC instants, entered IANA zone, mode, server status, optional staff-confirmed instant, created/updated timestamps. Reference enquiries are typed message attachments in the assigned advisor thread, not ViewingRequest rows.
- **AdvisorAssignmentDTO:** real account ID, public display identity, languages, declared availability/basis/updatedAt or unknown. Assignment changes revoke prior thread access unless an explicit audited handover policy retains it.
- **MessageDTO:** server ID, thread ID, authorized sender display/role, bounded plain text, createdAt, client idempotency token, typed attachments resolved on read. No HTML, staff-note reuse, automatic portfolio/Brief attachment or implied end-to-end encryption.
- **Data changes needed:** mixed-entry portfolio support, ordering/revision, assignment relationship, thread/messages with typed project enquiry context, explicit unit-viewing confirmation, message idempotency constraints. Parent/schema owner chooses migration details after contract review.

## Agreed implementation boundaries

Parent owns the dossier renderer/export adapter, safe login-return continuation and cross-flow integration. This discovery role later owns Office components and messages only when assigned; schema/API/thread contracts belong to their designated owners. No feature code starts from this document alone. Reference enquiries must enter the assigned advisor thread, and only REAL_REFERENCE project interests or authorized units are valid portfolio entries.
